# Secure Timeclock

A self-contained, open-source staff attendance application using **Employee ID, password authentication, GPS location, and server-side geofencing** for clock-in and clock-out.

Secure Timeclock is designed to provide a simple attendance workflow without dedicated attendance hardware.

It does **not** require biometric devices, QR kiosks, Bluetooth beacons, NFC, cameras, dedicated GPS hardware, external attendance terminals, or background location tracking.

The browser obtains the employee's location only when the employee attempts to clock in or clock out. The backend independently validates the submitted location and makes the attendance decision.

# What the Application Does

Secure Timeclock allows employees to record attendance from a web browser.

The basic workflow is:

1. The employee opens the application.
2. The employee enters their Employee ID and password.
3. The backend authenticates the employee.
4. The employee chooses **Clock In** or **Clock Out**.
5. The browser requests the employee's current GPS location.
6. The location is sent to the backend.
7. The backend checks:
   - whether the employee is authenticated;
   - whether the attendance action is valid;
   - whether the GPS reading is sufficiently accurate;
   - whether the location is recent;
   - whether the employee is inside an active attendance area;
   - whether the employee already has an open attendance session.
8. The backend accepts or rejects the action.
9. The official attendance time is generated by the server.
10. The attempt is recorded in attendance evidence and the audit trail.

The frontend is never trusted to make the final attendance decision.

# Core Principles

## 1. The backend makes the decision

The browser is treated as an untrusted client.

The frontend can request:

> "I want to clock in and this is the location my browser reported."

The backend decides whether that request is valid.

The frontend cannot simply tell the server:

> "I am inside the office."

## 2. Server time is authoritative

Employees do not supply the official attendance timestamp.

The application generates the attendance time on the server.

## 3. No background location tracking

The application does not continuously track employees.

It does not use `watchPosition()` or an equivalent continuous location-monitoring mechanism.

Location is requested when an attendance action requires it.

## 4. Attendance rules are enforced server-side

Changing or bypassing frontend JavaScript must not allow an employee to:

- clock in twice;
- clock out without clocking in;
- submit an arbitrary attendance time;
- bypass the geofence;
- bypass GPS accuracy checks;
- access HR-only audit information.

## 5. Rejections should be understandable

A rejected attendance attempt should explain:

**What happened**

> Your current location is outside the permitted attendance area.

**What to do**

> Move inside the configured attendance area and try again.

# Security Model

Secure Timeclock uses several layers of protection.

## Authentication

Employees authenticate using:

```text
Employee ID
+
Password
```

Passwords are never stored as plain text. They are hashed using **Argon2id**.

## Authorization

The backend determines what an authenticated user is allowed to access.

The application currently supports:

```text
EMPLOYEE
HR
ADMIN
```

Authorization is enforced by the backend rather than relying solely on hiding frontend controls.

## Password hashing

The database stores a `passwordHash` rather than the original password.

## Access tokens

Access tokens are short-lived. The default configuration is:

```text
15 minutes
```

## Refresh tokens

Refresh tokens are:

- randomly generated;
- stored as SHA-256 hashes;
- associated with an employee;
- given an expiration time;
- revoked during logout;
- rotated when refreshed.

The raw refresh token is not stored in the database.

## Login rate limiting

Redis is used to support login rate limiting and reduce repeated password-guessing attempts.

# Attendance Workflow

## Clock In

1. Sign in.
2. Select **Clock In**.
3. The browser requests the current location.
4. The location is sent to the backend.
5. The backend validates the request.
6. If all checks pass, a new attendance session is created.
7. The event is recorded in the audit/evidence records.

## Clock Out

1. Sign in.
2. Select **Clock Out**.
3. The browser obtains the current location.
4. The backend validates the location and attendance state.
5. The existing attendance session is closed.
6. The server records the clock-out time.
7. The event is recorded in the audit/evidence records.

## Duplicate clock-in prevention

An employee cannot create another open attendance session while an existing session is active. This is enforced by the backend.

## Invalid clock-out prevention

An employee cannot clock out if there is no open attendance session.

# Location and Geofencing

Secure Timeclock uses PostgreSQL with PostGIS for geographic calculations.

An attendance location is represented by:

```text
Latitude
Longitude
Radius
```

Example demonstration configuration:

```text
Office
Latitude: 5.6037
Longitude: -0.1870
Radius: 100 metres
```

These are demonstration values and must be replaced before real deployment.

## Location accuracy

GPS readings include an accuracy estimate. The system can reject a reading when the reported accuracy is worse than the configured maximum.

Example:

```text
Maximum allowed accuracy: 100 metres
Reported accuracy:        250 metres
```

The request can be rejected because the location evidence is too uncertain.

## Location freshness

The system checks how old the browser's location reading is.

The default configuration allows:

```text
120 seconds
```

A stale or invalid reading can be rejected.

## Geofence calculation

The backend calculates the distance between the employee's reported location and the configured attendance location using PostGIS geographic calculations.

The backend accepts the attendance action only when the calculated distance is within the configured radius.

Example:

```text
Configured radius: 100 metres
Calculated distance: 72 metres
Result: inside the attendance area
```

If the distance is 180 metres, the request is outside the configured attendance area and is rejected.

# Authentication

The login process uses Employee ID and password.

Example:

```text
Employee ID: 1000001
Password: ********
```

Employee IDs must be unique.

The application does not require an email address for basic authentication.

This makes the authentication model suitable for organizations that already use employee or staff identification numbers.

---

# Password Rules

The default password requirement is:

- Minimum 4 characters
- Letters and numbers only
- No spaces
- No special characters

Valid examples:

```text
Abcd
Pass1234
Employee2026
```

Examples that violate the default character rule:

```text
Pass@123
hello world
password!
```

Organizations can strengthen the minimum length and other requirements when customizing the application.

For a real production deployment, a stronger minimum password length should be used.

# Sessions and Tokens

### Access token

Short-lived token used to access protected API endpoints.

Default:

```text
15 minutes
```

### Refresh token

Longer-lived token used to obtain a new access token.

Default:

```text
7 days
```

Refresh tokens are rotated when used. The database stores only a hash of the refresh token.

# Audit Trail

Attendance decisions should be explainable.

Secure Timeclock records attendance evidence for accepted and rejected attendance attempts.

Evidence can include:

- Employee
- Attendance event type
- Result
- Server timestamp
- Latitude
- Longitude
- GPS accuracy
- Location timestamp
- Calculated distance
- Reason for rejection
- IP address
- User agent
- Associated attendance session where applicable

This allows an authorized administrator or HR user to understand what happened when an attendance decision is challenged.

### Accepted attempt

```text
Event: CLOCK_IN
Result: ACCEPTED
Accuracy: 24m
Distance: 41m
```

### Rejected attempt

```text
Event: CLOCK_IN
Result: REJECTED
Reason: OUTSIDE_GEOFENCE
Distance: 382m
```

# HR Audit View

Authorized HR users can review attendance audit records.

The audit view is intended to answer questions such as:

- Who attempted the attendance action?
- Was it accepted or rejected?
- When did the attempt occur?
- What caused the rejection?
- What location evidence was submitted?
- What was the calculated distance?
- Was the GPS accuracy acceptable?

The audit system is intended for **accountability and troubleshooting**, not continuous employee surveillance.

# Requirements

For local development, install:

- Git
- Docker
- Docker Compose

Node.js and npm are useful for directly running the applications outside Docker.

A modern browser with Geolocation API support is required for attendance actions.

The browser must be allowed to access location information.

For phone testing, use a secure HTTPS origin. Modern mobile browsers generally block
geolocation on ordinary HTTP pages served from a LAN IP. A local HTTPS reverse proxy
or a secure tunnel can be used during testing.

# Running the Application

## 1. Clone the repository

```bash
git clone <repository-url>
cd secure-timeclock
```

## 2. Create the environment file

```bash
cp .env.example .env
```

Edit `.env` and replace development secrets and passwords with your own values.

## 3. Start the application

```bash
docker compose up --build
```

Docker Compose starts the required services, including PostgreSQL, Redis, API, web application, and Nginx according to the project configuration.

## 4. Open the application

The Docker Compose setup exposes the application through:

```text
http://localhost:8080
```

The frontend uses the same-origin `/api` path, so the browser does not need to know the
Docker service address. This also makes the frontend suitable for phone access through
the same host when HTTPS is configured.

## 5. Seed development data

The seed requires:

```text
SEED_EMPLOYEE_PASSWORD
SEED_HR_PASSWORD
```

Set those values in your private `.env` file before running the seed.

Example:

```env
SEED_EMPLOYEE_PASSWORD=your-development-password
SEED_HR_PASSWORD=your-hr-development-password
```

Never commit the `.env` file.

# Production Deployment

This repository provides an open-source foundation. Before deploying it for a real organization, review the entire configuration and security model.

## Secrets

Generate strong random values for:

```text
JWT_ACCESS_SECRET
JWT_REFRESH_SECRET
```

Do not use development defaults.

## Database

Use a properly secured PostgreSQL deployment. Do not expose PostgreSQL directly to the public internet unless specifically justified.

## HTTPS

Production deployments should use HTTPS. Location access in modern browsers generally requires a secure context.

## CORS

Set `CORS_ORIGIN` to the actual production frontend origin.

Do not use a permissive wildcard unless specifically justified.

## Password policy

The default minimum password length is intentionally small for development simplicity. A real deployment should use a stronger password policy.

## Demo accounts

Remove or disable demonstration accounts before production use.

Never deploy with publicly documented demonstration credentials.

## Geofence

Configure the actual attendance location and appropriate radius.

Do not blindly use the demonstration coordinates or radius.

## GPS accuracy

Choose an accuracy threshold appropriate for the deployment. A very strict threshold can reject legitimate employees when GPS conditions are poor; a very loose threshold can reduce the usefulness of location evidence.

## Location freshness

Choose an appropriate maximum age for location readings based on operational requirements and expected device reliability.

## Monitoring

Production deployments should monitor:

- API availability
- Database availability
- Redis availability
- Application errors
- Authentication failures
- Resource usage
- Disk usage
- Database backups

## Backups

Configure regular PostgreSQL backups. A production attendance system should never rely on a single copy of its database.

# Security Considerations

## The frontend is not trusted

Users can modify browser JavaScript, inspect network requests, and manually construct API requests.

Therefore, important security decisions belong in the backend.

## GPS is evidence, not absolute proof

A GPS coordinate supplied by a browser is useful evidence of the device's reported location.

It is not a cryptographic guarantee that a particular human is physically standing at a particular location.

A determined attacker may attempt to manipulate location information through device or browser mechanisms.

Secure Timeclock therefore does not claim that GPS alone provides mathematically perfect proof of physical presence.

The system instead provides a practical application-level attendance control based on:

- authenticated employee identity;
- current location evidence;
- GPS accuracy;
- location freshness;
- server-side geofence calculation;
- attendance state;
- server-generated timestamps;
- audit records.

Organizations requiring stronger physical-presence assurance may need additional controls outside the scope of this application.

# What This Application Does Not Claim

Secure Timeclock does **not** claim to provide:

- Perfect proof of physical presence
- Continuous employee tracking
- Anti-spoofing that is impossible to defeat
- Biometric identity verification
- Hardware-backed location verification
- Detection of every form of employee collusion
- Protection against a compromised employee device

The goal is to provide a secure, transparent and practical software-based attendance system while keeping the system simple enough to understand, operate, and maintain.

# Privacy

The application deliberately avoids continuous location monitoring.

Location is requested for an attendance action rather than continuously in the background.

Attendance evidence can contain location information associated with the attendance attempt.

Organizations deploying this software should establish appropriate:

- Access controls
- Employee notices
- Legal and regulatory requirements

The appropriate retention period depends on the organization and jurisdiction.

# Troubleshooting

## Location permission denied

Check that the browser has permission to access location information.

On many browsers, location access also requires HTTPS unless the application is running on an allowed local development origin.

## Location accuracy is too low

The browser reported a location whose accuracy exceeds the configured limit.

Try:

- Moving to an area with better GPS reception.
- Moving outdoors or closer to an open area.
- Waiting briefly and trying again.

## Location reading is too old or invalid

The submitted location timestamp is outside the configured freshness window or is otherwise invalid.

Try the attendance action again so the browser obtains a fresh location.

## Current location is outside the permitted attendance area

The backend calculated that the submitted location is outside the configured geofence.

Move inside the configured attendance area and try again.

## Login fails

Check:

1. Employee ID
2. Password
3. Employee account status
4. API availability
5. Database availability
6. Redis availability
7. Environment configuration

Do not expose authentication details in application error messages.

# Project Philosophy

Secure Timeclock is built around a simple principle:

> **Verify what can reasonably be verified, record what happened, and explain the decision.**

The system should be secure without becoming unnecessarily complicated.

Employees should understand why an attendance attempt was accepted or rejected.

Administrators should be able to investigate a disputed attendance event.

Developers should be able to understand the code and operate the system without depending on proprietary hardware.

Organizations should be able to customize the application without changing its fundamental security model.
